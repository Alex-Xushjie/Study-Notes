# Linux 详细教材：沿一条 TCP 连接建立排错能力

[首页](../README.md) · [基础概念](01-Packet-Path.md) · [实验步骤](02-Labs.md)

## 1. 学完后必须能做什么

从客户端访问服务失败的现象出发，独立区分 DNS、选路、邻居解析、转发、过滤、监听和回程问题。能解释为什么路由器正常仍可能是主机问题；能用双端抓包支持判断，而不是试着重启所有设备。

前置知识：IPv4 子网、ARP、TCP 三次握手、静态路由。所有修改实验在专用 Linux VM 的 ncl namespace 中执行，先按原实验 L1 建立拓扑。

## 2. 先跟踪一次正常访问

客户端 ncl-c 为 10.10.0.2/24，路由器两侧为 10.10.0.1 与 10.20.0.1，服务端 ncl-s 为 10.20.0.2/24，HTTP 监听 TCP 8080。客户端访问 IP 地址时，这次实验不依赖 DNS。

第一步，应用创建 socket 并发起连接。内核必须决定源地址、出口和下一跳。目的地不在本地 /24，客户端把帧发给 10.10.0.1 的 MAC；IP 目的仍是 10.20.0.2。通过路由器后，二层头重新构造，TTL 减小，源/目的 IP 在没有 NAT 时保持不变。

第二步，路由器需要开启 IPv4 forwarding，并允许 FORWARD 路径。服务器收到 SYN 后，只有存在匹配地址和端口的监听 socket，才可能正常回应 SYN-ACK。服务器还需要通过 10.20.0.1 回到客户端。

第三步，TCP 建连不等于 HTTP 成功。三次握手完成后，应用还可能因权限、依赖、处理阻塞或请求格式而出错。网络排错必须把“能连接”和“请求完成”分开。

| 观测 | 可支持的结论 | 还不能证明 |
|---|---|---|
| 客户端有正确路由 | 本机有选路结果 | 下一跳和服务可达 |
| 服务端抓到 SYN | SYN 到达该抓包点 | socket 接受、回包到达客户端 |
| 客户端抓到 SYN-ACK | 回包到达该抓包点 | 应用已完成业务 |
| HTTP 返回预期内容 | 本次请求成功 | 持续负载与其他路径正常 |

## 3. 用命令建立正常基线

在 Linux VM 的不同终端执行，先保留完整输出，再摘录关键字段：

~~~bash
sudo ip netns exec ncl-c ip -br addr
sudo ip netns exec ncl-c ip route get 10.20.0.2
sudo ip netns exec ncl-c ip neigh
sudo ip netns exec ncl-r sysctl net.ipv4.ip_forward
sudo ip netns exec ncl-s ss -lntp
sudo ip netns exec ncl-c tcpdump -ni c0 -nn 'tcp port 8080'
sudo ip netns exec ncl-s tcpdump -ni s0 -nn 'tcp port 8080'
~~~

route get 重点读 via、dev、src，而非只看有没有 default。neigh 重点看下一跳状态；STALE 只是缓存状态，不等于失败。ss 重点看 LISTEN、Local Address、Port：127.0.0.1:8080 仅供本机 loopback 访问；0.0.0.0:8080 是 IPv4 通配监听，仍受防火墙等条件限制。

抓包标志中的 S 为 SYN，S. 为 SYN-ACK，R 为 RST。重复 SYN 只能说明客户端在重试，不能单独确定是链路、过滤还是回程。RST 常见于没有监听，也可能来自 reject 或中间设备，应核对来源与双端证据。

## 4. 完整故障推理：服务器收到 SYN，客户端没有回应

假设客户端重复发 SYN，服务器侧抓到 SYN，服务确实监听正确地址，但服务器没有在 s0 发出 SYN-ACK。先在服务器执行 ip route get 10.10.0.2。如果结果无可达路由，回程缺失是强线索；仍检查本机过滤与服务日志，避免把同时存在的第二故障忽略。

按原 L1 删除服务器 default，记录上述现象，再恢复。恢复后不仅 ping，还做一次 HTTP 访问并查看三次握手。报告应说明：正向报文能到，失败出现在服务器处理/回程范围；恢复路由后同一测试成功，支持回程路由为此次注入故障的原因。

反例：如果服务器抓到发出的 SYN-ACK 而客户端收不到，应把调查点移到中间路径；如果客户端已完成握手而 HTTP 不返回，应继续调查应用与数据阶段。不要固守最初猜测。

## 5. DNS：把名称解析单独验证

访问域名时先得到 IP，再连接服务。域名失败但 IP 正常时，应记录查询的 resolver、查询类型、返回码与耗时。NXDOMAIN 是名称不存在的响应；SERVFAIL 是解析服务失败；超时是没有在期限内收到有效响应，三者处理方向不同。

比较 dig example.com 与应用实际解析行为时，注意应用可能使用缓存、不同 resolver 或容器环境。A 与 AAAA 返回也可能引出不同路径。不要用一次 dig 正常排除应用内部 DNS 或 IPv6 问题。

练习：给一个错误 hostname 和一个不可达的实验 DNS 地址，比较“有否响应”“响应码”“耗时”。不要在工作站全局改 DNS；显式向实验 resolver 发查询。

## 6. MTU、MSS 与黑洞

MTU 限制三层包长度；TCP MSS 限制 TCP payload，并不包括 IP/TCP 头。普通 IPv4、无 options 时，1500 MTU 对应常见 1460 MSS。隧道增加外层头，如果底层预算未留余量，内层可用 MTU 会下降。

IPv4 测试 ping -M do -s 1472 的包长通常为 1472+8+20=1500。它只测试该路径、该时刻、该方向的 ICMP 条件。小 ping 成功、大文件卡住时，检查 DF、ICMP fragmentation needed、TCP 重传与实际包长。

黑洞的典型解释是：大包被丢弃，发送方又得不到必要的 PMTUD 反馈。区分实验可用递增包长、双端抓包、检查 ICMP 策略；不能只因为减小 MSS 后恢复，就宣布所有根因已确认。MSS 调整可能绕开问题，但隧道/策略仍需记录。

## 7. 策略路由、NAT 与状态防火墙

普通路由回答“目的在哪”；策略路由还可以根据源地址、mark 等选择表。检查顺序为 ip rule→命中表→表内最长匹配→实际出口。只检查 main 表可能漏掉关键规则。

INPUT 是送本机，FORWARD 是经本机。NAT 改地址并依赖相应连接跟踪关系；看到公网地址并不能说明内侧真实主机。记录抓包是在 NAT 前还是后，并用五元组追踪对应关系。

非对称路由并非天然错误，但当两方向经过不同的状态设备、或触发严格反向路径检查时会失败。正确修复需要理解安全要求与流量路径，不能默认关闭所有检查。

## 8. VLAN、bond 与主机性能

VLAN 子接口意味着本机参与标签处理，不代表交换机 trunk 已允许该 VLAN。检查物理口、子接口、交换机许可列表与抓包点。offload 可能影响本机看到的标签，必要时在另一侧观察。

active-backup bond 主要提供链路切换；LACP 需要对端协作，通常按 hash 分配流。两条 10G 的总容量不保证单条 TCP 连接达到 20G。断一成员后要同时验证逻辑接口、邻居、连接恢复与业务。

RSS 将流分到接收队列，IRQ/CPU 分布影响处理。先保存 ethtool 的队列、统计与 offload，以及 interrupts、softirqs；再观察测试期间的增量。GRO/TSO、checksum offload 会改变主机抓包形态，大包或校验和提示不能直接当线上异常。

一条流慢而多流总吞吐高，应调查单流限制、窗口/RTT、队列映射与 CPU；全流量都慢才继续比较链路、PCIe、NUMA 和整体资源。调优每次只改一个变量，并保留恢复值。

## 9. 练习与参考答案

1. ping 成功但端口拒绝，最先查什么？答案：服务监听地址/端口、RST 来源及本机 reject；ICMP 成功不能证明 TCP 服务。
2. 路由表正常而走错出口？答案：策略规则、源地址、namespace/VRF、相关表；使用包含正确上下文的 route get。
3. 服务端收到 SYN，是否可排除网络？答案：只能证明某一正向路径到抓包点，回程和后续数据仍未验证。
4. 增加接收队列后单流不变，是否功能失效？答案：单流常映射到一个队列；需要看多流分布和 CPU，而非只看队列总数。
5. 大包不通能否直接改全网 MTU？答案：先定位方向、瓶颈和隧道预算，用 ICMP/重传证据区分，再做范围明确的修复。

必交：L1/L2 基线；回程缺失和监听错误两份报告；一份 MTU 证据表；五道题不用原文复述。扩展：策略路由和 NIC 队列调查。
