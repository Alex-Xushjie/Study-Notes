# HPC 设计与实验：1000 GPU 方案

## H1 不需要 GPU 的反馈链作业

画发送 NIC、交换机入口/出口队列、接收 NIC。用不同颜色标出数据、ECN、CNP、PFC 的方向和作用范围。构造“所有 DSCP 都被归入默认队列”故障，说明你会从哪四个位置取证。

算一个数量级：400 Gbit/s × 2 µs ÷ 8 = 100,000 bytes。它只是这段时间发送的数据量，不能作为交换机 PFC headroom 的最终配置。列出还缺的参数：链路传播、pause 反应、frame/MTU、ASIC 管线、缓冲模型等。

## H2 1000 GPU 的完整容量例题

**教学假设，不是 NVIDIA 参考设计或采购推荐**：125 台服务器，每台 8 GPU；每台有 8 个 400G 网络端点，一 GPU/端点映射到一个 rail。共 8 个 rail；每 rail 有 125 个服务器端点。数据 fabric 不包含管理/存储网络。

采用每台 leaf 64×400G 的假设端口能力，32 下行 + 32 上行：

| 项目 | 每 rail | 8 rail 合计 |
|---|---|---|
| 服务器端点 | 125 | 1000 |
| leaf | ceil(125/32)=4 | 32 |
| 可用下行口 | 128（使用 125） | 1024（使用 1000） |
| leaf-spine 链路 | 4×32=128 | 1024 |
| spine | 4，每台接每 leaf 8 条 | 32 |
| 每 spine 使用端口 | 4×8=32 | 全网 1024 个 spine 端口 |

每 leaf 下行容量最大 32×400G=12.8 Tbit/s，上行同为 12.8 Tbit/s，设计比例 1:1。某 rail 第四台 leaf 只接 29 个端点，因此该 leaf 实际接入负载低于端口满配值。一个 spine 故障会令每 leaf 上行由 32 条降至 24 条；满接入 leaf 的下行/上行为 32/24≈1.33:1。

注意：每 rail 放四 spine 是本例的故障域选择，并非端口最少的唯一方案。计算量级和端口可行不表示无阻塞性能已证实，还要看交换芯片结构、ECMP 分布、实际通信模式和布线。

总物理数据链路：服务器→leaf 1000 条，leaf→spine 1024 条，共 2024 条。在每条链路两端都用独立可插拔光模块的假设下，需要 4048 个收发器；DAC/AOC、breakout 及不同速率会改变 BOM，不能把此数字直接用于采购。

rail-optimized 是根据节点内部 GPU/NIC 关系及通信模式组织网络。这个简化例中的 rails 相互独立，跨 rail 如何通信、库如何利用节点内部互联是必须验证的假设。不要把“双网卡接两 leaf”自动理解成所有流量无损切换或带宽翻倍。

交付补充：GPU/NIC/PCIe/NUMA 映射、L3/ECMP 策略、QoS 映射表、故障后容量、管理/存储网络、遥测、扩容单位。没有服务器内部拓扑就不能完成最终设计。

## H3 两条实践路径

### 路径 A：暂无 RDMA/GPU 硬件

完成 H1/H2，并分析以下**模拟数据**，不要写成自己测出的结论：

| 场景 | 业务吞吐相对基线 | pause duration | ECN/CNP | 假设 |
|---|---|---|---|---|
| 单对单 | 100% | 低 | 低 | 建立基线，未必覆盖拥塞 |
| 多对一 | 45% | 显著上升 | 很少 | 标记/反馈/阈值/队列映射值得检查 |
| 恢复映射后 | 75% | 降低 | 增加 | 反馈可能起效，仍需排除其他变量 |

每行写两个备选原因、区分它们需要的证据和下一次只改一个变量的实验。可选 Soft-RoCE 学 API/连通性，但不能据此验证 ASIC PFC 或真实 NIC 性能。

### 路径 B：有两台匹配 NIC 的 Linux 实验机

1. 记录 `lspci`、`ethtool -i`、`rdma link show`、`ibv_devinfo`、MTU、GID、IP、驱动和固件；工具可能来自 rdma-core/perftest 等包，先核验实际安装。
2. 先验证 IP 可达与链路错误，再按 `ib_write_bw --help` 核对 device、port、GID index 与 RoCE 地址模式。在两端使用相同参数和兼容版本，一端 server，一端连接 server IP。
3. 依次测单 QP、小/大消息、多 QP，再增加并发对。每次记录吞吐单位、CPU、时长、方向、拓扑、ECN/PFC/丢包计数增量。
4. 有 GPU/CUDA/NCCL 与相应通信环境后，按 nccl-tests 项目 README 构建并测 collective。区分单机多 GPU 与多机；单机成功不证明网络 RDMA 成功。
5. 故障实验每次仅改一个变量，在隔离环境测试拥塞与单链路中断，恢复配置并重跑基线。

复用已有 [RDMA 实机笔记](../../AIDC/lab.md) 作为命令背景，但其中接口、地址与版本必须换成自己实验环境。

## H4 400G/800G 与光模块核对

为一条服务器链路和一条 fabric 链路分别填写：交换机端口能力、NIC 端口能力、QSFP-DD/OSFP 外形、lane 数/速率、光学 PMD、距离、光纤类型、连接器、极性、FEC、breakout 支持、两端兼容矩阵。外形相同不保证兼容，端口标“800G”也不表示任意 2×400G breakout 都可用。

本项目不列动态价格与具体采购料号。选定型号后到两端设备/模块官方兼容矩阵核对，再决定 BOM。

最终验收：20 分钟说明需求→125 台服务器→rail/端口数量→正常与故障容量→拥塞控制→测量方案→未知条件。能指出本例简化假设，比背一个拓扑更重要。
