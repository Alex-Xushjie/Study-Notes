# 设计、Solutions Engineering 与英文表达

这是原对话中 Architect/SE 方向的贯穿练习，使用每周既有的设计/英文时间，不再另加一条课程。

## 需求访谈：先问业务，再选技术

场景：客户说“我们要一个低延迟、高可用的云和数据中心网络”。先明确业务流、地点、规模、时延/吞吐目标、允许中断、增长、合规/隔离、现网限制、预算、人员和交付时间。把“高可用”改写成故障条件与可测的恢复目标；目标数值由需求确定，不由产品宣传决定。

一页需求表的示例：

| 需求 | 可测试表述 | 未确认假设 | 验证方式 |
|---|---|---|---|
| 可用性 | 单 CE 故障后关键服务在约定时间内恢复 | 客户可接受短连接重建？ | 断 CE 后业务探测 |
| 分段 | Dev 不能主动访问 Prod | Shared 是否可同时访问二者？ | 五元组矩阵正反测试 |
| 性能 | 指定负载下 p99 满足目标 | 包长与并发模型？ | 固定负载重复测量 |

## HLD 的固定结构

1. 业务需求、范围、成功标准和待确认事项。
2. 逻辑/物理拓扑与故障域，地址、租户、路由、安全、DNS。
3. 正常流量路径与至少四个故障场景。
4. 容量与 N-1 剩余能力，测量口径和计算过程。
5. 两个可选方案的收益、约束、成本组成和运营代价。
6. 部署/迁移顺序、回退点、观察窗口与验收。
7. 监控、告警、权限、配置管理与后续扩容。

LLD 再补接口/地址/邻居、策略条目、设备版本和具体命令。HLD 不应该只有厂商图标，LLD 不应该只是没有说明的配置堆叠。

## PoC 与供应商比较

PoC 用真实需求导出测试，不挑最容易成功的演示。每项包含输入负载、预期、操作、证据、通过阈值和恢复步骤。明确哪些是功能验证、哪些是性能验证。

比较供应商时使用同一业务标准：功能与版本支持、故障行为、自动化接口、可观测性、光模块/生态兼容、支持模式、交付周期、五年成本构成。没有报价时给成本项目，不编造价格。

客户质疑“为什么要花钱做第二接入地点？”可以先指出当前共同故障域，再展示单地点故障影响和备选方案。面向管理层用业务影响解释，不用更多缩写淹没问题。

## 每阶段设计题与参考要点

| 阶段 | 题目 | 好答案必须出现的内容 |
|---|---|---|
| Linux | TCP 偶发慢，交换机说没丢包 | 应用/socket/主机/网络观测、双端抓包、offload 限制 |
| 自动化 | 500 台设备如何做健康检查？ | 并发与限流、超时、schema、UNKNOWN、预期 inventory、证据 |
| Cloud | 两 DC、两 Azure 区域如何互联？ | 故障域、双向路由、DNS、安全、容量、专线/备份取舍 |
| Edge | 双 ISP，主 ISP 变慢但没断 | 测量、策略、入出方向、抑制抖动、回切、验证 |
| DC | EVPN 邻居都 up，租户不通 | underlay→RT/VNI→MAC/IP→主机逐层检查 |
| HPC | 1000 GPU 网络如何设计？ | 业务/节点拓扑假设、端口预算、rail、拥塞、N-1、基准 |
| Trading | 开盘几秒 gap，上联平均很空 | microburst、NIC/socket、A/B 序号、观测精度、RCA |

## 英文练习方法

每周录一次 3–5 分钟说明，用同一成果作材料。结构：*Requirements → Assumptions → Packet path → Failure scenario → Validation → Trade-off*。先保证技术准确与条理，再修语法和语速。

不要背一段完美英语后换题就不会讲。让自己追加两个追问：*What evidence would disprove your assumption?* 和 *What happens if the backup path also has reduced capacity?*

## 作品集与履历

优先选三个能完整讲述的项目：自动化健康检查、混合云/边界网络设计、HPC 或交易网络专项。每个用“问题→限制→方案→验证→结果→反思”讲述。

练习项目标记 lab/design study；只有实际完成且有数据时才写具体改进百分比。不要把教材的示例吞吐、模拟故障或 1000 GPU 设计写成已交付生产项目。
