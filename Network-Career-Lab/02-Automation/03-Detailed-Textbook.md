# 自动化详细教材：把人工判断变成可验证程序

[首页](../README.md) · [入门导读](01-Learning-Guide.md) · [原项目与运行命令](02-Project.md)

## 1. 自动化到底在解决什么

人工登录 100 台设备执行 show 命令，问题不只有耗时，还包括漏设备、判断口径不同、缺少原始证据和失败后无人察觉。程序应把工作拆成 inventory→采集→规范化→判断→报告→退出状态，每一层有独立输入和输出。

先不做批量配置。第一份项目只读，离线构造正常与异常数据，把判断写对，再接一台实验设备。已有 health_check.py 是 BGP 起步实现，不是已实现全部十二项的生产平台。

## 2. Python 最少要掌握哪些概念

字符串表示设备名、地址和状态；整数/浮点数表示计数与时延；bool 表示明确真假；None 表示缺值，不能直接等于健康。list 存放多台设备，dict 表示带字段的一条记录。for 用于逐条处理，if 用于分支，function 用于让同一判断可被测试。

~~~python
records = [
    {"device": "edge-1", "state": "Established"},
    {"device": "edge-2", "state": "Idle"},
    {"device": "edge-3", "state": None},
]

def classify(record):
    state = record.get("state")
    if state is None:
        return "UNKNOWN"
    if state == "Established":
        return "PASS"
    return "FAIL"

for record in records:
    print(record["device"], classify(record))
~~~

这是独立的逻辑教学例，不是原项目 schema。预期三行分别是 PASS、FAIL、UNKNOWN。尝试把 state 拼成 State，程序会进入 UNKNOWN：这说明字段名是契约，不是随便写的说明文字。

dict.get 适合可能缺失字段，但必要字段仍应验证；否则拼写错误会长期被当作缺数据。字符串 "0" 与数字 0 不同，JSON null 进入 Python 后为 None。学习顺序为读数据→遍历→纯函数→异常→文件→模块，暂不需要 Web 框架。

## 3. 定义数据契约，再写采集器

一条观测至少要知道来自谁、什么时刻、哪个平台、什么对象、值是什么、采集是否成功。意图数据描述“应该有谁”，观测描述“看到谁”。两者必须分开，不然一个彻底消失的邻居连异常都不会被发现。

| 数据类别 | 示例字段 | 为什么需要 |
|---|---|---|
| 意图 | device、expected_peers、enabled_interfaces | 防止只遍历实际输出而遗漏缺失对象 |
| 元信息 | timestamp、platform、version、schema_version | 判断时效、解析器与兼容性 |
| 采集 | status、error、duration | 区分采集失败与设备状态异常 |
| 观测 | peer、state、prefix_count | 供判断规则使用 |
| 判定 | check、result、reason、evidence | 便于人复核，不只输出红绿灯 |

实际项目先阅读 sample.json，再按既有接口增加字段；不要把本表中的概念 schema 不经适配直接喂给起步程序。若修改 schema，同时修改样例、验证和说明。

缺失设备、陈旧数据、采集失败属于 UNKNOWN；明确观测到预期邻居 Idle 属于 FAIL；不适用指标可以 N/A，但必须由平台能力/范围明确决定，不能把错误一律改为 N/A。

## 4. 接设备之前先学失败处理

网络采集可能发生连接超时、认证失败、权限不足、输出截断、API 限流或解析错误。一个 except 捕获所有错误再返回空列表，会让故障变成“没有要检查的对象”。应该返回结构化错误并保留原因，报告中明确哪些设备没有有效观测。

重试仅适合可能恢复的短暂故障，并要有次数、退避和总时限。认证失败重复尝试可能无益。并发不能无限开大：假设单台平均 2 秒，100 台串行为约 200 秒；并发 10 的理想下限约 20 秒，但实际还受尾部超时、限流和设备负载影响。该计算只用于估算，不是性能承诺。

凭据由环境变量、交互或受控凭据系统提供，不写进 inventory 与报告。日志记录设备与错误类型，避免输出完整 token。只读账号也要验证实际权限与命令支持。

## 5. 完整项目：新增接口与 CRC 检查

第一步为意图要求启用的接口定义 admin/oper 预期。关闭的备用口不应告警。admin up、oper down 与 admin down 分别表示不同问题，应保留原始值。

第二步处理累计计数器。假设 t1 为 1000，t2 为 1030，间隔 60 秒，在确认同一设备启动周期且计数有效时，增量是 30，速率是 0.5 次/秒。不能看到 1030 就说“本分钟发生 1030 次”。如果 t2 小于 t1，检查重启、清零或回绕，当前窗口标不确定并重建基线。

第三步为每项写测试：正常、明确故障、缺字段、设备缺失、计数器倒退、样本过期。测试应表达业务契约，例如“预期设备未出现必须返回 UNKNOWN”，而非只是证明某个函数被调用。

第四步把原始输入、程序版本、判定时间和报告一起保存。报告可覆盖旧输出，但原始证据应有唯一时间标识。退出码约定沿用原项目：0 全通过；1 有 FAIL；2 输入错误或仅有 UNKNOWN。退出码与详细原因都要检查。

## 6. 从 Python 到 Ansible、Jinja2

Python 适合规范化和复杂判断，Jinja2 把意图渲染成文本，Ansible 编排步骤。Netmiko、NAPALM、REST API 是接入选择，需按平台与功能支持挑选；不要为了工具齐全强行同时使用。

渲染流程先检验必填字段，再生成候选配置，人工检查 diff，然后做设备基线检查，最后在实验目标应用并进行后验检查。已有 render.yml 只写本地文件，不会替你完成网络设备事务或回退。

幂等指重复执行不造成额外变化；不等于配置正确。check mode 也不保证等同真实执行，具体取决于模块支持。重复执行无 changed 是一个观察，还需验证最终状态符合意图。

## 7. 变更安全为何属于技术能力

以修改双边 BGP 策略为例：如果一次推全网，把错误过滤器扩散到所有出口，恢复通道可能同时丢失。把变更拆为一台实验设备→一个小批次→验证→扩大，并事先保存配置与带外恢复入口。

前验包括邻居状态、关键路由、探测与管理通道；后验除语法与会话状态外，还要验证前缀数量、关键下一跳、业务路径与意外传播。触发回退的条件需要预先定义，如关键探测连续失败或必要前缀消失，具体阈值由业务决定。

Git 保存可审查差异和意图历史，但把文件 git revert 不等于设备已经恢复。设备恢复依赖 NOS 支持、连接方式和明确操作。每次演练把“源文件回退”与“设备恢复”分别验证。

## 8. 排错案例：全部 PASS，实际一台设备离线

错误实现只遍历采集成功的列表，离线设备没有记录，所以全通过。修复不是加一个 print，而是用预期 inventory 与实际集合做差集，产生 missing_device 的 UNKNOWN。然后加入回归样例，确认退出码非零。

另一个陷阱是 BGP 邻居全部 Established，但业务前缀被过滤。状态检查只证明会话，不证明前缀、下一跳和转发；按业务意图增加关键路由和探测，而不是把同一检查换个名字重复做。

## 9. 练习与参考答案

1. 空列表可否判 PASS？答案：取决于意图，若预期有设备/邻居则不允许；必须检查预期集合。
2. 超时应该 FAIL 还是 UNKNOWN？答案：采集超时意味着无法判断被检状态，可另建采集可用性检查，但不能把缺观测等同正常。
3. 为什么 CRC 要双采样？答案：累计值不提供当前窗口变化，且要处理重启/回绕。
4. 模板成功生成能否发布？答案：还缺语义、diff、前验、应用方式、回退和后验。
5. 脚本突然慢了先增加线程吗？答案：先分解连接、执行、解析耗时与超时尾部，检查限流和设备负载。

必交：读懂原程序的数据路径；实现或设计一项接口检查和一项增量检查；准备故障样例；完成一次离线配置 diff 审查。实机采集与下发为具备平台后的扩展，不声称本书已经实现。
