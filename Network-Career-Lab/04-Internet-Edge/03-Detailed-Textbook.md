# Internet Edge 详细教材：策略、路由安全与故障处置

[首页](../README.md) · [基础导读](01-Design-and-Security.md) · [FRR 实验](02-Labs.md)

## 1. 从“BGP 会建立”到“边界可运营”

边界工程师不只建立邻居，还要明确从谁接收哪些路由、向谁发布哪些前缀、故障后流量走哪里，以及错误策略会影响谁。先理解商业关系和策略，再讨论命令。

Transit 提供约定范围的互联网可达性；peering 通常交换双方及约定客户路由，不应默认理解成免费全表。IXP 是互联场所/交换平台，连接 IXP 不表示自动与所有成员交换路由。route server 简化会话关系，但数据通常不经过 route server 本身；具体策略依运营方安排。

## 2. 教学拓扑与策略意图

企业 AS65010 接 ISP-A AS65001 和 ISP-B AS65002，企业文档前缀 203.0.113.0/24。所有地址/ASN 仅用于隔离实验，不能向公网宣告。

先写意图表：企业只发布自己拥有的 /24；默认优先 A 出站，A 失效使用 B；禁止把 A 学来的路由转发发布给 B；入站优化只作影响，不能承诺远端必选某线路。

| 方向 | 意图 | 所需检查 |
|---|---|---|
| 从 A/B 接收 | 按实验范围接收默认或约定前缀 | 收到、策略通过、下一跳可达 |
| 向 A/B 发送 | 仅本企业 /24 | export 白名单与实际 advertised routes |
| 本地出站 | A 优先、B 备份 | local-pref、最佳路由、FIB、业务路径 |
| 外部入站 | 按对端支持影响 | 外部观测、community 支持和回程 |

不要在还未验证 export 的情况下接收全表并开放发布。默认拒绝、逐条许可更容易说明边界。max-prefix 控制异常规模，但不替代具体前缀过滤。

## 3. BGP 的排错层次

TCP/会话层先看连通、ASN、源地址、TTL/auth 等条件。Established 后，再看该 AFI/SAFI 是否启用，是否收到了目标前缀，import 策略是否允许，路由是否最佳，下一跳是否可解析，是否进入系统路由和 FIB。

例如 BGP 表有两个相同 /24，local-pref 较高的 A 被选为 best；但下一跳失去可达性时，结果取决于实际控制面处理。不要仅凭 BGP 表有一条记录就断言可转发。应比较 BGP RIB、系统路由与数据面探测。

将观测分开保存：neighbor summary、目标前缀明细、接收/发布视图、策略命中、route/FIB、traceroute/业务探测。某些 received-routes 视图依赖功能或配置，按实验 FRR 版本核验。

## 4. 出站控制与入站影响

Local preference 在自己的 AS 内表达路径偏好，常用于出站选择。企业给 A 学来的前缀更高 local-pref，表示本地倾向把去往这些目的地的流量交 A，不代表远端回包也经 A。

AS-path prepend 在发布方向增加路径长度，可能影响别人选路，但对方 local-pref 或其他策略可以优先于长度。MED 的比较范围和策略依实现与对等条件，不能当作全互联网统一旋钮。

发布更具体前缀利用最长匹配，但受对端过滤、授权和可接受前缀长度约束，也增加路由规模与运维复杂度。不能把任意拆分前缀当万能流量工程。应先问对端支持哪些 communities，再设计可观测、可回退的调整。

## 5. 防止自己变成非预期 transit

危险场景：A 路由进入企业，企业原样发布给 B，B 于是可能把到 A 侧的业务流量送进企业。两边 BGP 都正常，但企业成为不希望承担的中转点。

正确验证必须在 B 侧看到企业仅发布自有前缀，在 A 侧同样检查。只在企业侧查看 route-map 文本不足以证明实际发布结果。可给 A 放一个文档测试前缀，在 B 检查不应出现来自企业的传播路径，再记录正向自有前缀仍正常。

业务可达与路由泄漏是两个不同验收项。一个 ping 成功无法证明 export 正确。

## 6. RPKI 与 ROA：逐条手算

ROV 检查前缀起源授权，不验证完整 AS path，不判断链路性能。实际验证基于验证器提供的有效载荷。基本分类为：存在匹配授权则 Valid；有覆盖授权但无匹配起源/长度则 Invalid；没有覆盖授权则 NotFound。NotFound 不等于恶意。

教学授权：203.0.113.0/24，origin AS65010，maxLength=24。

| 收到的路由 | 结果 | 原因 |
|---|---|---|
| /24，origin 65010 | Valid | 起源和长度匹配 |
| /24，origin 65020 | Invalid | 覆盖存在但起源不匹配 |
| 203.0.113.0/25，origin 65010 | Invalid | 比 maxLength 更具体 |
| 198.51.100.0/24，origin 65010 | NotFound | 假设无其他覆盖授权 |

若另有一条覆盖且正确匹配的授权，需要按全部有效记录判断，不能看到一个不匹配记录就直接判 Invalid。实施还要验证缓存更新、验证器可用性与实际策略，不能只在白板写“启用 RPKI”。

## 7. DDoS：先确定拥塞发生在哪里

若接入电路在到达本地设备前已经被打满，本地 ACL 丢包不能恢复电路容量。处置可能需要上游 RTBH、FlowSpec 或清洗，具体依合同和运营方能力。

RTBH 通过约定机制把目标流量丢弃，通常牺牲受攻击目标的可达性保护其他业务。FlowSpec 可以描述更细粒度匹配和动作，但错误规则可能误伤；必须限制来源、匹配范围、传播边界和撤销方式。清洗还涉及引流、回注路径、MTU、状态设备与容量。

演练单按以下顺序填写：受影响目标与时间→电路/设备/应用瓶颈→可用上游能力→规则范围与预期副作用→授权与执行人→验证→撤销→复盘。教材只做隔离实验或桌面演练，不向真实运营商发送处置请求。

## 8. 故障案例：主线变慢但 BGP 不断

会话存活只表明控制连接存在。主线可能有拥塞、丢包或应用特定路径问题。先对比多目的、多时间窗的业务测量，区分远端服务、DNS、单个前缀与普遍链路问题。

若证据支持 A 的路径质量下降，可在实验里提高 B 的 local-pref，观察出站 best/FIB 与业务。不要频繁随样本抖动切换；切换条件、观察窗口与回切条件需提前定义。入站可能仍经 A，因此报告分别写出两个方向。

## 9. 作业与参考答案

必修：原 E1 建好三节点；保存两侧实际发布前缀；修改 local-pref 验证出站变化；撤掉 A 验证收敛和业务恢复。各记录控制面与业务恢复时间，不把前者替代后者。

推演：把自有 /24 从 export 白名单删除，预测邻居仍 Established 而外部失去目的路由；恢复后检查实际发布与外部探测。再给四条 ROA 例题自己改 origin/maxLength 重算。

自测一：为什么 prepend 不保证入站？答：远端独立策略可能覆盖路径长度。自测二：NotFound 要不要默认当攻击？答：不是授权有效性结论之外的安全判决，需明确运营策略。自测三：BGP 正常可否排除网络问题？答：不行，控制面与数据面、性能分别验证。自测四：ACL 能否解决所有带宽攻击？答：若上游电路已饱和，本地丢弃不能释放该段容量。
