# 云网络详细教材：从地址规划到混合云双向路径

## 1. 把熟悉的网络概念迁移到云

VPC/VNet 可以先理解为客户控制的逻辑网络范围，但不要直接等同一台交换机。云中的路由、安全组、子网 ACL、网关和托管服务分别承担不同职责。图上两对象连接，不表示自动产生双向可达。

本章核心能力是给定一条业务流，列出名称解析、源地址、路由表、下一跳、安全策略、转换和回程。第一轮全部可用纸面设计完成；真实云验证必须另记区域、版本、实际配置与资源账单。

## 2. 地址规划先于创建资源

教学企业有本地 10.10.0.0/16、AWS Prod 10.20.0.0/16、AWS Dev 10.30.0.0/16、Shared 10.40.0.0/16。地址不重叠只是起点，还需预留区域、环境、增长与收购空间。按“地域→环境→子网用途”建立台账，比随手取三个 /24 更便于汇总和排错。

若两个业务都使用 10.20.0.0/16，路由系统不能仅凭目的地址分辨意图。可选择重编号、代理、特定 NAT 或服务级连接，但每个选择都会影响 DNS、日志、访问控制和运维。不要先画全互联，再在最后一页写“地址冲突待解决”。

子网用途应明确：应用、数据、入口、网关接入或管理。云平台保留地址与子网限制以平台文档为准，不能直接照搬物理网络可用地址算法。

## 3. AWS 基础路径

对外访问通常涉及子网路由和相应网关。指向 Internet Gateway 的路由本身不保证一个只有私有 IPv4 的实例能直接互联网通信；还需正确的公网地址映射和安全条件。NAT Gateway 为私网发起的适用流量提供地址转换，不等于给私有实例开放任意入站服务。

公有/私有子网的关键是路由与访问方式，而非名字。给子网命名 public 不能改变其实际路径。NAT 放在哪个故障域、应用子网选哪个 NAT、故障时是否跨区，都会影响可用性、流量路径与成本构成。

安全组是有状态控制；NACL 是子网层的无状态控制。以客户端 10.10.1.10:53000 访问 10.20.1.20:443 为例，反向报文目的端口是 53000。NACL 设计必须考虑该反向临时端口，不能只允许两个方向目的端口 443。实际端口范围按系统和应用核验。

## 4. TGW：关联与传播不是同一件事

关联决定报文从某 attachment 进入 TGW 时使用哪张 TGW 路由表；传播决定该 attachment 的路由被装入哪些 TGW 路由表。把 A 的路由传播到一张表，不代表 A 的流量就查询那张表。

教学需求：Prod/Dev 都可访问 Shared，但彼此不能互访。本地可访问 Prod/Shared，不能访问 Dev。可建立如下逻辑表，真实安全控制仍需防火墙/安全组与验证。

| 入口 attachment | 关联的 TGW 表 | 表内允许存在的目标 |
|---|---|---|
| Prod | RT-Prod | Shared→Shared attachment；本地→VPN/DX 路径 |
| Dev | RT-Dev | Shared→Shared attachment |
| Shared | RT-Shared | Prod、Dev、本地各自 attachment |
| 本地 | RT-OnPrem | Prod、Shared 各自 attachment |

Prod→Shared 的流程：Prod 子网表把 10.40/16 指向 TGW→从 Prod attachment 进入并查询 RT-Prod→发送到 Shared attachment→Shared 内部路由/安全→服务。回程由 Shared 子网表→RT-Shared→Prod 完成。漏掉任一侧的子网表，TGW 表全对也会失败。

这里 Shared 可以返回 Dev 与 Prod，并不意味着 Dev 可借 Shared 随意转发到 Prod。还要禁止不需要的转发/代理路径，审查 Shared 是否承担中转功能。这是分段设计中的重要反例。

## 5. DNS 是混合云的一部分

连接打通后，私有域名仍可能解析失败，或解析到客户端不可达的地址。画出客户端 resolver、条件转发、云侧入站/出站解析端点和目标 zone。避免两边都把同一个后缀转发给对方造成循环。

验收至少包含名称解析、返回地址所属网络、到该地址的实际路径以及应用访问。记录缓存 TTL 和故障后旧记录的影响。不要用公共 DNS 的成功响应证明私有域正常。

## 6. Azure hub-spoke：有 peering 不等于中转成立

hub 放共享连接与安全能力，spoke 放业务。两个 spoke 都 peering 到 hub，不自动意味着 spoke 之间传递。需要根据目标架构设计 UDR、转发能力、gateway transit 等相应条件。

假设 Spoke-A 10.60/16 与 Spoke-B 10.70/16 要经过 hub 防火墙。正向路径要求 A 的有效路由把 B 前缀送往防火墙，防火墙有到 B 的路由并允许该流，B 的回程也应按设计返回。只改 A 的 UDR 可能导致正向经防火墙、反向绕过，影响状态检查。

排错用 NIC 有效路由和有效安全规则确认实际状态，而不只看你刚编辑的那张表。若使用 NVA，还需检查转发配置、健康探测、负载分担和会话状态的实现。具体路由优先级与服务约束应以选定版本和服务文档为准。

## 7. 专线不是一条线的图标

AWS 混合云需要明确物理连接、VIF、Direct Connect Gateway 与 TGW 等逻辑关系；连接到 TGW 的场景不能省略中间逻辑组件。Azure ExpressRoute 同样要分别说明电路、连接、对等与网关，不把一个电路内的冗余连接等同异地冗余。

设计双本地机房、双接入地点时，逐项询问：是否同运营商、同管道、同建筑、同电源、同 CE、同云侧接入位置？备份 VPN 依赖互联网，是否与主路径共享故障？谁负责监控、切换和回切？

容量例：两条 10G 平时各承载 6G，总负载 12G。任一失效后只剩 10G，因此即使路由可收敛，业务仍可能拥塞。可增加容量、降低关键负载或设计故障时优先级。不能把“有备线”写成“故障无影响”。

## 8. 故障案例：云端收到请求，但本地应用超时

先核对抓包/流日志支持的方向与时间，不能只看一个 ACCEPT。检查云端回应是否发出、云端返回路由、TGW 入口关联表、专线/VPN 传播、本地防火墙和本地回程。若存在 NAT，核对日志里的地址是原始还是转换后。

构造路由矩阵：每行是一条五元组业务流，每列依次是解析、源子网表、TGW/UDR、边界路由、安全规则、目的服务与反向路径。在第一个没有证据的格子补观测，比在控制台随意改规则更有效。

## 9. 必修作业与参考答案

作业一：按本章地址完成四张 TGW 表与四类 VPC 子网路由，逐条写 Prod→Shared、Dev→Shared、本地→Prod 及回程；再证明 Dev→Prod 无允许路径。

作业二：设计 Azure 两 spoke 经 hub 防火墙的五元组矩阵，分别制造缺 UDR、错误安全规则、错误 DNS 的纸面案例，说明每种会留下什么观测。

作业三：设计双 10G 的 N-1 验收，区分路由恢复时间与应用恢复时间。没有真实资源时交付推演和待验证清单。

自测：传播到表就会被所有入口使用吗？答案：不会，入口关联决定查询表。安全组放行就一定能通吗？答案：还需路由、其他策略、服务和回程。双连接是否容忍站点故障？答案：要检查物理共同点。IP 正常而域名失败先看什么？答案：解析链、返回地址、缓存和私有 zone/转发配置。
