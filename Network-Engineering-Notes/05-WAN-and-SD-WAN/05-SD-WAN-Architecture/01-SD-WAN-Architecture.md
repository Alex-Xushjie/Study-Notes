# SD-WAN平面、边缘与控制依赖

[返回WAN与SD-WAN目录](../WAN-and-SD-WAN.md)

## 1. SD-WAN的核心能力

SD-WAN通常把多承载接入、Overlay连接、集中策略和路径质量感知结合起来。它是一类架构和产品能力集合，不是一种所有厂商共用的路由协议。双WAN静态主备能实现部分冗余，但并不等于具有完整的策略、可观测性与生命周期管理。

| 平面 | 工作内容 | 故障问题 |
|---|---|---|
| 管理 | 配置、模板、监控、审计与软件维护 | 管理平台失联能否继续转发？ |
| 编排/引导 | 身份注册、上线、连接协调 | 新设备能否加入、NAT后能否发现？ |
| 控制 | 分发路由、拓扑、策略及相关安全信息 | 既有与新路由何时失效？ |
| 数据 | 边缘封装、加密、选路与安全执行 | 实际包从哪条路径走？ |

一个产品可以合并某些平面。管理系统常不在用户数据路径上，但SASE安全节点或Hub可能在；不要把所有云端节点都叫控制器。

## 2. Underlay到Overlay

边缘先获得传输IP、网关、DNS/时间等依赖，再建立管理/控制联系、完成身份验证，随后获得路由和策略，建立相应数据连接。每一步单独可用不代表下一步必然成功。

Underlay只需使相关端点可达，不应默认承载全部企业业务前缀。Overlay路由传播与数据隧道形成可能采用不同状态，因此控制连接UP但数据隧道DOWN是合理的故障组合。

## 3. 边缘身份与站点

站点ID、设备ID、证书/序列号、组织归属与传输定位用于不同功能。两台同站点设备需要正确的HA与路由设计，不能简单克隆所有标识。错误组织、重复ID、证书时间或吊销状态，都可能阻止上线。

企业需掌握证书轮换、授权、备份、平台账号和恢复流程。平时只会推模板，控制平台故障时却不知道哪些状态能保留，是能力缺口。

## 4. 控制面失联

既有流量可能按缓存路由和密钥继续，也可能在保留计时、Rekey、策略期限或隧道事件后失败。新站点、新路由、新密钥和变更可能受影响。不能统一断言“控制器断了业务永远不受影响”。

测试管理平台、控制节点、编排节点分别失效，以及冷启动、链路变化和长时间失联。记录实际版本、保留计时和观察窗口，避免只测30秒就下结论。

## 5. 练习

画上线依赖图与平面故障矩阵，标出哪些节点真正承载业务。回答：为什么能登录Manager仍不能通业务？为什么旧流通而新增站点失败？为什么时间错误会影响上线？
