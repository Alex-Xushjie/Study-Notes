# 封装开销、MTU与大包黑洞

[返回WAN与SD-WAN目录](../WAN-and-SD-WAN.md)

## 1. 先明确报文长度所在层

物理口MTU、IP MTU、隧道可承载的内层IP长度和应用消息大小不同。IPsec开销随外层IPv4/IPv6、NAT-T、算法、IV、认证标签、填充和其他封装变化，不能给所有隧道套一个固定“减60”值。

教学假设外层路径IP MTU=1500，明确选定的总封装开销H=74字节，则内层IP最大长度按1500−74=1426字节预算。若内层IPv4/TCP均无选项、首部各20字节，基础MSS预算为1386。H只是题目给定值，必须用实际封装核对。

## 2. MSS不修复所有流量

MSS影响TCP建立连接时协商的数据段大小，不能直接修复UDP、ICMP或所有已存在会话。TCP选项、IPv6首部和额外扩展也需考虑。端点可用PMTUD/PLPMTUD等机制，但ICMP错误被过滤、应用不支持或隧道反馈不正确，都可能出现小包通、大包卡。

IPv4 DF相关处理与分片位置取决于设备设置；IPv6路由器不替发送者分片。用“让路由器一直分片”作默认修复会增加负担并掩盖路径规划问题。

## 3. Linux测量示例

在实验Linux中先确认route和接口。下面10.20.0.10是实验远端主机，不是公网测试目标。

~~~bash
ip route get 10.20.0.10
ping -4 -M do -s 1200 -c 3 10.20.0.10
ping -4 -M do -s 1400 -c 3 10.20.0.10
tracepath -n 10.20.0.10
~~~

ping的-s是ICMP负载；无IPv4选项时通常还加20字节IP和8字节ICMP。成功只能证明该协议、方向和采样窗口，失败还可能是过滤或限速。tracepath依赖探测反馈，不保证每个WAN都给出完整MTU。

## 4. 排错流程

保存源端发送长度、隧道内外层抓包、接口MTU、分片/重组与丢弃增量；找出从哪个长度开始异常。比较双方向、两条线路与是否经过安全服务。隧道切到蜂窝后才卡顿，要核对新的Underlay MTU而非只改原专线配置。

大文件失败也可能是吞吐、TCP窗口或应用超时；通过包长阶梯和报文反馈区分。修改MSS后新会话改善，不足以证明UDP业务已恢复。

## 5. 验收

覆盖小包、规划上限、超限包、TCP、UDP、双向和备线路。记录所选参数的依据与恢复原值的方法。最终交付“实际封装组成—可用内层MTU—各业务行为”表，避免只留一行tunnel mtu命令。

[PMTUD：RFC1191](https://www.rfc-editor.org/rfc/rfc1191.html)、[IPv6 PMTUD：RFC8201](https://www.rfc-editor.org/rfc/rfc8201.html)、[数据报PLPMTUD：RFC8899](https://www.rfc-editor.org/rfc/rfc8899.html)。
