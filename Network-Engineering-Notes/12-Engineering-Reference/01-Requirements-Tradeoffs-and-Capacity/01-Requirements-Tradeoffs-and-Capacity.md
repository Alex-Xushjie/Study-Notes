# 需求访谈、取舍与可验收目标

[返回本部分学习目录](../Engineering-Reference.md)

## 1. 从问题和约束开始

“建设SD-WAN”“升级无线”“优化低延迟”是方案方向，不是充分需求。先问谁在什么场景遇到什么问题、影响多大、如何确认改善，再收集预算、时限、既有能力、合规/安全、停机窗口和恢复条件。

| 需求项 | 待填写内容 |
|---|---|
| 业务/负责人 | 用户、服务、站点、关键时间窗 |
| 当前问题 | 可复现动作、范围、频率与证据 |
| 目标 | 成功率、延迟/恢复/完整性，测量口径 |
| 容量 | bps/pps、并发、包长、峰值与增长 |
| 安全 | 身份、隔离、数据与审计边界 |
| 约束 | 预算、设备、团队、授权与维护 |
| 验收 | 环境、负载、阈值依据、双方确认 |

## 2. 目标必须有边界

“零中断”“无丢包”“纳秒级”“全网自动化”若无条件不可验收。改写为指定业务、负载、故障、采样、测量点和允许恢复范围，区分目标、合同承诺与当前测试结果。

RTO是恢复时间目标，RPO涉及允许数据损失范围，网络只能承担其中一部分。业务SLO和设备/线路SLA不同，不能拿供应商可用率直接当应用保证。

## 3. 方案取舍

比较至少两个可行方案，按同一安全、可用性和容量目标评估成本、复杂度、人员与恢复。未满足硬约束先排除，不能用大量低权重优点掩盖关键不适用。

## 4. 假设与未知

每项假设有来源、置信/影响、验证方法和负责人；未知不是填一个漂亮默认值。没有硬件/现场/供应商数据时，结论写“设计待验证”，不把推演写成验收通过。

## 5. 练习

将“办公室Wi-Fi很慢”与“开盘行情gap”分别改写为需求表、候选解释和验收契约。先明确测量，不急着买AP或改内核参数。
