# MLAG与vPC：把共享状态与故障域拆开

[路由交换学习目录](../Routing-and-Switching.md)

## 1. 多机聚合解决什么问题

普通LAG对端通常是一个逻辑协商系统。MLAG、vPC等让两台协作交换设备提供跨机聚合能力，以支持双归属接入。它们不是完全相同的协议，状态同步、双活保护和故障恢复按厂商/版本解释。

双设备协作不意味着所有控制面、路由表和升级行为都变成一台交换机。不要从主机看到一个聚合身份，反推网络内部没有共同故障点。

## 2. 对象与流量

| 对象 | 职责与问题 |
|---|---|
| Peer状态 | 两台交换机是否按预期协作 |
| Peer-link | 同步及特定数据承载；不能假定永远只有控制流 |
| Keepalive/独立检测 | 在相应实现中辅助区分peer失联/双活等情况 |
| 双归属端口 | 下游跨两设备组成聚合 |
| Orphan/单归属端口 | 仅接一侧，故障行为与双归属不同 |
| 一致性 | VLAN、端口参数及相关功能是否匹配 |

keepalive活着不表示peer-link可用，也不表示所有租户数据正常。独立检测若与peer-link同故障域，可能失去设计价值。[Arista MLAG模型](https://www.arista.com/en/um-eos/eos-multi-chassis-link-aggregation)

## 3. 逐个故障推演

单成员断：下游LAG重分配，检查剩余容量。整台设备掉电：双归属与单归属受影响不同。Peer-link断但peer仍活：要观察保护策略与端口处理，而不是期待两端都继续无条件转发。检测通道同时失效：需分析双活风险与具体保护边界。

不要用一个厂商的“secondary挂起”规则概括另一厂商所有场景，运行手册应记录版本、角色、条件与恢复顺序。

## 4. 网关与路由是另一层

下游聚合成立，不代表SVI、VRRP/Anycast Gateway、上游路由与防火墙状态同时正确。故障时数据可能跨peer-link绕行，需计算其实际容量，并验证回程与单归属服务。

升级或重启后的保护等待可防止不完整状态过早投入，但等待时间与服务恢复目标要一起设计，不能只把等待调为最短。

## 5. 案例与证据

双归属服务器正常、单归属存储异常：优先比较共同故障与peer-link数据路径，而非统一重建服务器LACP。保存两台peer/端口/VLAN/MAC/路由状态和同时间业务探测。

验收至少覆盖peer-link、独立检测、整机、单归属、回切及非对称恢复。实际命令使用对应平台手册；本文没有部署跨厂商互联或承诺无损升级。
