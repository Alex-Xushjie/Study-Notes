# 路由授权、ROV与DDoS处置边界

[路由交换学习目录](../Routing-and-Switching.md)

## 1. 把四种安全问题分开

地址/ASN归属与授权、起源公告是否合法、传播关系是否合规、转发流量是否攻击，是不同问题。单靠RPKI、IRR或ACL任一个机制都不能覆盖全部。

IRR路由对象常用于生成过滤依据，但数据质量与授权维护需核实；RPKI的ROA表达起源授权，相应验证器生成有效载荷供路由器使用。ROV不是验证整条AS路径，也不是性能检测。

## 2. 手算ROV

教学授权：203.0.113.0/24，origin AS65010，maxLength24，假定有效载荷完整且无其他覆盖记录：

| 公告 | 结果 | 原因 |
|---|---|---|
| /24，origin65010 | Valid | 起源和长度均匹配 |
| /24，origin65020 | Invalid | 有覆盖但无匹配起源授权 |
| 203.0.113.0/25，origin65010 | Invalid | 超出最大长度 |
| 198.51.100.0/24，origin65010 | NotFound | 无覆盖记录 |

若存在另一条允许当前公告的覆盖授权，应按全部记录判定，不能看到一条不匹配就直接Invalid。NotFound不等于恶意；Valid也不证明没有路由泄漏。[RFC6811](https://www.rfc-editor.org/rfc/rfc6811.html)

## 3. 验证器与策略是运行系统

记录验证器冗余、RTR连接、数据时效、失联/过期行为和路由策略。不能只写“开启RPKI”。发布/变更ROA要与实际起源AS和更具体公告配合，防止把自己的合法业务变成Invalid。

过滤范围还需包含自身授权、对端角色和约定路由长度。私有/保留空间等过滤要按真实边界设计，不能把公共互联网模板原样用于私网对等。

## 4. 上游电路满时本地丢弃的限制

攻击在到达本地之前已占满接入链路，本地ACL无法释放那段容量。先确认瓶颈在链路、设备控制面、转发资源还是应用，再选择相应处置。CoPP主要保护设备控制面，不等于万能清洗。

RTBH通过约定公告让上游丢弃目标流量，通常会牺牲该目标可达性；必须限制授权目标和作用范围。BLACKHOLE community有标准说明，但运营商是否接受、怎样执行仍需约定与验证。[RFC7999](https://www.rfc-editor.org/rfc/rfc7999.html)

FlowSpec可表达更细的匹配/动作，但有误匹配、错误传播、资源和兼容风险。只在受控来源、授权范围、验证与撤销机制完善的条件使用。[RFC8955](https://www.rfc-editor.org/rfc/rfc8955.html)

## 5. 桌面演练

目标P受到UDP攻击：记录时间/量级/合法流→确认上游能力→选择目标与匹配→评估副作用→限定传播/持续时间→执行责任→外部与业务验证→撤销→复盘。清洗方案另需回注、MTU、状态设备和容量。

不向真实ISP发送教材测试。误黑洞整个/24时，要能从实际路由/业务影响发现并按既定通道撤销，而不是等客户报障。

## 6. 交付

输出ROV例题、起源/长度/传播过滤矩阵、验证器故障推演和一份含撤销条件的DDoS Runbook。自测：Valid是否认证完整路径？答：不是。收到blackhole community是否证明上游执行？答：不是。文中所有案例是设计演练，未进行公网实验。
