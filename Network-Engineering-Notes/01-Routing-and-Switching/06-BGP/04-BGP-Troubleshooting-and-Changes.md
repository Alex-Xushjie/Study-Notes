# BGP排错与安全变更：从会话到业务

[路由交换学习目录](../Routing-and-Switching.md)

## 1. 按六层定位

| 层 | 先问什么 | 观测 |
|---|---|---|
| TCP/源地址 | 谁用哪个地址连谁 | 路由、ACL、抓包、日志 |
| OPEN/能力 | ASN与地址族是否协商 | 通知、邻居明细 |
| 接收/import | 对方是否发布、自己是否允许 | 两端前缀与策略 |
| 最佳/递归 | 路径是否有效、为何未选 | 属性与下一跳 |
| RIB/FIB | 是否被别的来源覆盖或下装失败 | 路由、硬件/内核表 |
| 数据与回程 | 业务能否完成 | 双向探测、状态设备、应用 |

## 2. 四个案例

A：Established但前缀0。区分对端没起源、地址族没激活、import拒绝、max-prefix/策略状态等；不是直接改hold timer。

B：有路径却不是best。比较资格、local-pref、AS_PATH、ORIGIN/MED条件和内部距离等；确认观察的是同一前缀，而不是拿默认路由与/24比较。

C：best但数据黑洞。查RIB/FIB、递归邻接、discard、策略与返回。实验ISP用Null0起源时，本来不能用该前缀ping证明业务，需后挂真实主机。

D：切到备ISP后仍有连接失败。出站、入站和会话状态可能变化不同步；查反向、NAT、防火墙、MTU与备线容量，不只看BGP稳定。

## 3. 变更前后验证

定义允许接收/发布集合、关键前缀和业务，保存基线、diff、回退与带外。先单邻居/小故障域，核对实际发布与外部观测，再扩大；同批更改所有出口会同时扩大错误传播与恢复风险。

Soft refresh不等于零代价，hard reset不等于唯一重新应用方式。明确触发回退条件、观察窗和回切，避免自动化在短暂样本间反复切换。

## 4. 路由泄漏推演

企业接A/B，只准公告自有P。给A增加实验Q，确认企业能按意图接收，但B不能从企业学到Q。只验证P可达不能证明没有泄漏。

角色与OTC等机制可辅助防泄漏，但需要双方支持和正确关系，不能替代边界白名单。[RFC9234](https://www.rfc-editor.org/rfc/rfc9234.html)

## 5. 输出

交付六层证据、一个属性改动、一次撤路/故障恢复和发布边界证明。不要为日志方便直接清全表或反复重建全部会话。所有案例为教学情境，未在本次实跑。
