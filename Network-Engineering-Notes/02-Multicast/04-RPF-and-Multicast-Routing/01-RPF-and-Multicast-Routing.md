# RPF检查、MRIB与组播转发

[返回组播学习目录](../Multicast.md)

## 1. RPF问的是从哪里来

Reverse Path Forwarding（反向路径转发）用朝上游目标的路由信息确定期望入接口及上游邻居，帮助建立无环树和排除错误方向数据。对源树(S,G)，目标通常是S；对共享树(*,G)，上游通常朝RP。不要把组播G当成普通单播目的地址去找默认路由。

MRIB是组播路由信息基础，可能由单播RIB导入、专用组播路由或策略形成；MFIB是组播实际转发状态。多数简单部署复用单播路由，但“有单播路由”与“组播实际采用该路由”不是同义词。

组播RPF与主机/路由器的单播uRPF防源欺骗功能不同。二者都涉及反向路由思路，却有不同配置对象、用途和丢弃证据。

## 2. 具体推导

LHR到S有两条路：经核心A成本10，经B成本20，RPF选择A。数据却从B进入时，普通源树转发可能丢弃。先回答为什么走B：非对称拓扑、静态组播路由、ECMP选择、上游尚未收敛还是错误VRF？不能只因S可ping就跳过此步。

若树是(*,G)，应另外查向RP的RPF；切到(S,G)后方向可能改变。一个报文同时涉及共享树和源树状态，平台可能通过继承与排除规则计算有效OIL，不能把两个show列表简单拼接。

## 3. 检查顺序

1. 固定VRF、S、G与采样时间，确认实际源地址没有NAT或双网卡变化。
2. 查向S及RP的路由：前缀、下一跳、递归、出接口与有效性。
3. 查组播选用的RPF接口、PIM上游邻居及邻接。
4. 对照实际入包接口和RPF丢弃增量。
5. 查OIF、下游Join/本地成员、硬件安装，再验证数据离开。

## 4. 不能滥用静态mroute

静态组播路由可能改变RPF选择，用于明确的组播拓扑设计，但它不是看到丢包就填的万能命令。错误静态项可使主备路径不再跟随单播收敛；只修一台设备还可能造成相邻节点选择不一致。

设计时记录覆盖前缀、优先级、下一跳可达性、备份条件和撤销方式。若业务需求是独立组播拓扑，应把它作为受控路由设计，而非隐形例外。

## 5. 验收

在双上联拓扑分别断A、恢复A、断B，观察RIB/MRIB、RPF、Join、MFIB及应用序列号时间线。测量真实流量恢复，不用路由表收敛时间替代。硬件RPF与聚合逻辑接口的呈现以平台为准。

[FRR PIM与RPF命令](https://docs.frrouting.org/en/latest/pim.html)、[PIM规范](https://www.rfc-editor.org/rfc/rfc7761.html)。
