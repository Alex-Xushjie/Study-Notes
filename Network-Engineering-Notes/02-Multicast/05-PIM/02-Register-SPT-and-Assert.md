# Register、SPT切换与Assert排错

[返回组播学习目录](../Multicast.md)

## 1. 把封装流和原生流分开

Register外层目的地址为RP，内层仍是源S发往G的数据。抓包时分别匹配外层PIM和内层业务，不能用“到组G的UDP数量”统计全部注册流量。封装引入额外长度，隧道/链路MTU与策略也可能影响初始过程。

Register-Stop后仍可能通过Null-Register探测维持状态，具体时序取决于协议计时与实现。控制面有周期性报文不意味着所有业务数据一直绕RP封装。

## 2. SPT切换

LHR根据策略向S发(S,G) Join，并在满足切换条件后从共享树路径转向源树，再剪除不需要的共享树源流量。门限、是否立即切换及显示Flag依平台而异。不要把“存在(S,G)”直接等同“接收流量已经从SPT进入”。

SPT是路由度量下的树，不自动保证最低物理延迟。IGP cost、链路传播、转发方式、队列和主机处理都影响实际时延。量化设计要测正常及切换时的丢包、重复、乱序和尾延迟。

## 3. Assert解决什么

共享LAN上可能有两台路由器都向同一网段转发同一源流，造成重复。Assert根据路由相关度量和地址等规则选择相应转发者；它是针对具体树/流的转发协调，不能当成所有组共用的单一DR。

出现重复包时检查重复最早出现在哪个观察点、是否只有特定(S,G)、是否与拓扑变化重合。也可能是源本身重复、A/B合流未去重、镜像采集重复或应用重放，不能看到重复就只查Assert。

## 4. 四类症状

| 症状 | 区分步骤 |
|---|---|
| 源LAN有包，RP无Register | 查FHR角色、PIM启用、RP映射、Register路径及过滤 |
| RP收到Register，接收者仍无包 | 查接收树、解封与原生路径、OIF和成员 |
| 开始能收，切SPT后断 | 查RPF(S)、源树路径、MTU/ACL和硬件下发 |
| 稳态正常，新组加入失败 | 查RP冷启动依赖，不先归因于应用 |

## 5. 练习输出

提交三张简图：Register单播方向、共享树数据方向、SPT数据方向。每张画出对应路由查找目标和抓包点。让一个源前缀仅在接收侧错误选路，验证“RP可达但SPT失败”的区别；修改仅在隔离实验域进行。
