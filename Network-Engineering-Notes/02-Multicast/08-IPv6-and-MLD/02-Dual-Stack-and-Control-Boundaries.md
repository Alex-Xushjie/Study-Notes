# 双栈组播与控制边界

[返回组播学习目录](../Multicast.md)

## 1. 两套服务分别验收

IPv4成员报告不会自动生成IPv6成员；IPv4 PIM树正常不证明IPv6 RPF、RP映射或转发已启用。双栈应用可能在某栈失败后依旧提供另一栈数据，从而掩盖问题。监控应标记地址族、频道和实际接收路径。

台账按栈分别列S/G/P、VRF、成员版本、Querier、RP/SSM范围、接口和边界策略。不要凭一个“multicast enabled”的界面状态完成验收。

## 2. 作用域、Hop Limit与安全

作用域限制表达可传播范围，Hop Limit控制最大转发跳数，二者不是同一机制。管理作用域和组织边界还要落实到路由器与承载策略。将业务地址分配成看似内部范围，不能保证云隧道、代理或网关不会把内容带出。

基础ICMPv6、MLD和PIM控制报文应按需要处理，业务UDP另列白名单。过度宽泛放行和一刀切丢弃都不构成可运营方案。检查CPU保护策略是否会在启动风暴时误丢成员控制报文。

## 3. MTU与包长

同样UDP负载在IPv6中有不同IP首部开销。IPv6路由器不替发送端进行分片，发送端与应用需正确处理包长及错误反馈；组播发送者对多个接收路径的可见性和反馈能力还有限。优先以明确的端到端最小MTU规划业务报文，避免依赖隐式碎片行为。

隧道/加密进一步吃掉MTU。测试包含小包、接近规划上限的包和明确超限的包，记录源端、隧道口与接收端结果。只有小包成功不足以排除包长问题。

## 4. 故障练习

设置同频道IPv4正常、IPv6失败，候选原因分别为MLD被过滤、IPv6 PIM未启用、SSM源地址错误、作用域错误、包长超限。每次只注入一项。诊断需要给出能区分这些原因的观察点，而非一次性放开所有策略。

## 5. 交付要求

提供双栈能力表及每项成功/失败证据；若镜像不支持IPv6 PIM，明确标记未验证，保留MLD主机侧实验即可。不要用IPv4测试结果填补IPv6数据。

[IPv6规范：RFC8200](https://www.rfc-editor.org/rfc/rfc8200.html)、[IPv6作用域：RFC4007](https://www.rfc-editor.org/rfc/rfc4007.html)、[MLD Snooping背景](https://www.rfc-editor.org/rfc/rfc4541.html)。
