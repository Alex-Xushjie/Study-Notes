# 组播设计与分层排障

[返回组播学习目录](../Multicast.md)

## 1. 从业务需求开始

设计输入至少包括源数、频道数、接收者分布、峰值bps/pps、突发包长、允许gap/延迟、冷启动要求、故障域、安全与跨域边界。先确定同VLAN还是跨路由、源是否已知、是否支持源过滤，再选ASM/SSM与冗余，而不是先挑设备命令。

| 维度 | 需要回答 | 对设计的影响 |
|---|---|---|
| 成员规模 | 同时多少组、多少(S,G)、每组多少出口？ | 控制面、ASIC表项和复制资源 |
| 数据规模 | 峰值、突发和小包pps是多少？ | 链路、队列、NIC与CPU |
| 恢复要求 | 旧流、新源、新接收者各允许多久？ | RP、查询、路由与应用策略 |
| 故障域 | 是否共电源、光缆、节点、配置系统？ | A/B真正独立程度 |
| 权限 | 谁可发、谁可收、谁维护频道？ | 边界过滤、源限制、应用认证 |

## 2. 一条排错主线

先从应用确定受影响channel、S/G/P、时间窗、序号区间、服务器范围，再沿源到接收者定位第一个不一致点。对每一跳同时拿状态和数据，不跳到全局计时器调优。

1. 源进程：真的发送了吗，源IP、出口、TTL、端口和包长正确吗？
2. 源接入：正确VLAN上有数据吗，FHR是否收到，源是否被过滤？
3. 建树：ASM查RP/Register和共享树，SSM查指定源Join；确认模式匹配。
4. 每跳转发：RPF目标/接口正确吗，OIL有下游吗，硬件是否安装，丢弃在哪里增长？
5. 接收接入：IGMP/MLD、Querier、Snooping成员/路由器口是否正确？
6. 主机应用：NIC、内核、Socket、防火墙、订阅接口和处理速度是否正常？

## 3. 按影响范围缩小

| 范围 | 优先比较 |
|---|---|
| 所有组、所有接收者 | 源/公共链路/域级策略/整体容量 |
| 一个组所有接收者 | 频道源、G映射、特定树、组过滤 |
| 一个主机所有组 | 接入口、网卡、主机/进程资源 |
| 同VLAN部分接收者 | 成员口、Fast Leave、端口拥塞 |
| 只有新组/新源失败 | 查询与冷启动、RP源发现、表项容量 |
| 开盘突发时失败 | 小窗口队列/NIC/Socket与应用积压 |

这是排查优先级，不是根因判决。共享源出问题也可能只影响一个频道；设备表项用尽可能只影响后创建的组。

## 4. 变更原则

建立正常与异常基线，提出可被推翻的假设，用一个变量区分。每次记录原值、预期结果、观察窗口和回退条件。全局关闭Snooping、扩大TTL、清空所有组播表或提高所有Buffer可能掩盖问题并扩大影响，不能当作常规第一步。

验收不仅是恢复收包，还包括无关组无回归、无成员端口没有异常泛洪、故障恢复与冷启动符合目标、资源占用可持续。配置输出只是证据的一部分。

## 5. 学习成果

交付拓扑、频道台账、正常状态、至少三个故障注入、逐跳证据、RCA与回退。使用[实验报告模板](../../../Network-Career-Lab/08-Portfolio/Lab-Report-Template.md)。实际未测试的部分写“待实测”，不要用教材推演冒充生产经历。
