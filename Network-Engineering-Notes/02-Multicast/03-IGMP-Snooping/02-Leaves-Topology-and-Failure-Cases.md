# 离组优化、拓扑变化与间歇故障

[返回组播学习目录](../Multicast.md)

## 1. Fast Leave的适用条件

Immediate/Fast Leave在收到离开意图后快速删端口，可以减少无用流量，但前提是这个端口后面的成员关系足够明确。单台接收主机直连端口与下挂交换机、无线AP、虚拟化宿主机、共享链路完全不同。

同一端口后有R1和R2时，R1离开不意味着R2不再需要G。若设备不能可靠跟踪每个接收者，立即删口可能切断R2。Explicit Host Tracking可提高精细度，但是否覆盖所用版本、拓扑和失联场景必须验证，不应因有此选项就全局开启优化。

## 2. 链路恢复为何仍断流

交换机重启可能丢失动态成员与路由器口，链路恢复后接收进程没有重新启动，也就不一定立刻产生新的主动加入。后续Query和报告才能重建成员。STP变化、MLAG切换时，厂家可能临时泛洪、主动查询或刷新状态，不能套用固定恢复时长。

维护窗口记录四个时间点：物理恢复、控制邻接恢复、成员/复制表恢复、应用序列号恢复。不要只报告端口UP到端口UP为0秒。

## 3. 三个故障案例

| 现象 | 首选假设 | 区分证据 |
|---|---|---|
| 应用启动可用，数分钟后断 | Querier缺失或报告未刷新 | Query缺失、表项年龄与断点吻合 |
| 一台终端退出，另一台断流 | 共享端口误用Fast Leave | 同口多成员、离开后端口整体被删 |
| 交换机倒换后只部分组恢复 | 状态同步/容量/源过滤兼容 | 分组对比软件表、硬件表与计数 |

每个假设都要保留反证。例如Query存在但发在错误VLAN，仍属于有效查询缺失；Query存在且主机持续报告，则应转查Snooping解析、版本与硬件安装。

## 4. 变更与回退

变更前导出VLAN内当前成员数、Querier、mrouter端口、未知组播策略和资源占用。选一个测试组、一台测试接收者、一个无关对照端口，先测试加入与退出，再测试有损与倒换。回退需要恢复原策略并确认动态状态重新学习，不只是撤一行命令。

静态成员口可作为明确、记录在案的特殊配置，但会长期复制，增加容量与授权边界风险。用静态口临时恢复时，应单独记录真正根因尚未消除。
