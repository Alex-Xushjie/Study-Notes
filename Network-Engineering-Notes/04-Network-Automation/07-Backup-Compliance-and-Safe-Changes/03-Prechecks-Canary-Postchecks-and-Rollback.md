# 变更前检、灰度、后检与回滚

[返回网络自动化目录](../Network-Automation.md)

## 1. 安全变更闭环

输入校验→采集基线→生成计划/Diff→审查→前检→小范围执行→后检→扩大批次或恢复。各阶段有可追溯的版本、对象和结果。自动化放大正确操作，也会放大错误目标与错误假设。

| 阶段 | 必须回答 |
|---|---|
| 计划 | 改哪些设备/资源，哪些由工具拥有？ |
| 前检 | 身份/版本/基线是否与计划一致，管理与备份是否可用？ |
| 灰度 | 哪个站点/故障域最先变化，观察多久？ |
| 后检 | 配置、协议、路由、安全与业务是否符合预期？ |
| 失败 | 停止哪批、已生效多少、何时触发回退？ |
| 完成 | 持久化、文档/SoT/监控是否一致？ |

## 2. 风险分组

核心双机、Hub、同一维护域、上下游依赖不能只按清单每10台随意分批。Canary应具有代表性，同时控制影响面。一个小型接入设备通过不代表核心的硬件/协议行为相同。

## 3. 备份与回滚不同

备份是恢复资料，回滚是已验证的动作和路径。逆向命令未必恢复原状态，全量覆盖可能丢失并发变更。commit-confirmed、Checkpoint或配置会话各有范围与限制，多设备不能默认原子提交。

断开唯一管理路径后，脚本未必能执行回退，需要设备侧保护或带外/现场恢复。定义失败超时、停止条件和人工接管，不用无限重试挽回。

## 4. 非破坏的学习项目

先选择实验接口描述变更，不先练批量改默认路由、AAA或管理ACL。即使描述变更也要检查字符、范围与日志，不使用输入构造额外CLI。教学项目不自动执行生产发布。

后检至少对照实际配置和业务；命令返回成功只代表某一执行层通过。持久化running到startup也可能是独立步骤，确认平台行为后再纳入流程。

## 5. 演练交付

模拟第2台执行失败、第一台已生效，报告应列已完成/失败/未执行，不称全量已回滚。再模拟后检失败但命令成功，证明流水线会停止。提交前检表、计划、审查记录、执行台账和恢复证据。

设备生产变更按既有组织授权执行；教材示例只是使动作可审查、可验证的方法。
