# 模型校验、配置漂移与变更归属

[返回网络自动化目录](../Network-Automation.md)

## 1. 格式Schema与业务约束

JSON Schema、类型模型或自定义校验可约束字段类型与结构；跨设备地址唯一、链路两端关系、ASN/VRF归属、生产隔离等还需业务逻辑。类型校验成功不代表能安全部署。

Schema变更需迁移与版本策略。旧版本输入要么显式转换，要么明确失败；未知字段是拒绝还是保留，要按契约决定，不能随库默认行为漂移。

## 2. 漂移有四种解释

期望与实际不同，可能是未经授权修改、紧急恢复尚未回写、采集/解析错误或期望数据过时。先分类再处置，不把所有差异都自动纠正。尤其生产故障刚临时绕行时，自动覆盖可能再次中断。

| 差异 | 应问的问题 |
|---|---|
| 意图有，设备缺 | 设备是否纳管、数据是否完整、功能是否支持？ |
| 设备有，意图缺 | 是未管理字段、遗留还是应删除？ |
| 同值不同格式 | 是否只需语义归一化？ |
| 无事实数据 | 是未知，不是确认不存在 |

## 3. 确定性与所有权

相同输入快照、模板和工具版本应生成相同结果。排序、默认值、时间戳和随机ID不要让每次渲染产生无意义差异。生成物记录run_id和哈希可以放元数据，而不是不断改设备描述触发配置变更。

字段/资源所有权要明确：接口描述归自动化，路由策略归另一团队时，自动化不能以整块replace删除对方内容。多工具管理同一对象需有协调或锁定规则。

## 4. 并发与过期计划

计划生成后真实状态可能改变。发布前重新校验设备身份、数据版本、基线与变更范围；支持版本条件的API可用条件写入。超过有效期、输入哈希变化或基线不匹配时暂停执行并重新生成计划。

## 5. 练习

设计一个只管理接口description的工具，面对未纳管接口、未知状态和手工描述变化时分别输出“忽略/待审核/拟修改”，不自动扩展管理范围。用两次相同输入证明输出确定性。

[JSON Schema概念](https://json-schema.org/understanding-json-schema/)、[NetBox对象与API](https://netbox.readthedocs.io/en/stable/integrations/rest-api/)。
