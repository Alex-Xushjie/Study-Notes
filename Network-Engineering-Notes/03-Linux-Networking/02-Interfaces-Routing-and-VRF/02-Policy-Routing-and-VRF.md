# 策略路由与VRF进阶：多网卡主机怎样选择出口

[Linux专题目录](../Linux-Networking.md) · [前置：读懂网卡、地址与普通路由](01-Interfaces-and-Routing.md)

本篇为进阶阅读。请先能解释ip、接口名、dev、via、src和main表，再进入下文；首次学习Linux时先读前置篇。

## 1. 学习目标与边界

你已经知道跨网段需要路由，也知道路由器按最长前缀匹配转发。Linux需要进一步回答：查哪张表、使用哪个源地址、接口处于什么状态、下一跳是否可交付，以及应用是否处于正确的VRF。

读完本篇，应能分析三个问题：接口UP但业务不通；main表有正确路由但流量仍走另一出口；VRF路由正确但应用连接失败。Namespace、bridge、过滤与socket后续会单独展开，本篇只在路径需要时指出这些边界。

命令使用现代iproute2语法。接口名和地址按实验环境替换；所有输出均为简化教学示例，不是本次实测结果。不同内核、驱动、发行版和iproute2版本的显示可能不同。

## 2. 先把Linux对象与已有知识对应

| Linux对象 | 分析时关心什么 | 容易混淆的点 |
|---|---|---|
| 网络接口 | 链路类型、状态、MTU、上下层关系 | 一个名字不一定对应一个物理端口 |
| 地址对象 | 哪个接口持有什么地址，地址是否可用 | 有地址不等于远端可达 |
| 路由表 | 在该表内目的前缀如何到达 | main并非所有流量唯一使用的表 |
| RPDB规则 | 哪些条件触发哪种查表或动作 | 规则优先级不是路由metric |
| 邻居表 | 选定出口上的下一跳如何二层交付 | 查的是下一跳，不一定是最终目的 |
| VRF | 哪些接口与应用流量使用哪套路由域 | 单独建一张路由表不等于完整VRF关联 |
| Namespace | 当前命令观察哪套网络状态 | 宿主结果不能代替容器结果 |

这些对象需要串成路径，而不是分别记命令。最实用的描述是：“某进程在某network namespace中，以某源地址和VRF上下文访问目标，RPDB引导查询某表，得到出口、下一跳及后续交付条件。”

## 3. 接口：先看关系，再解释状态

### 3.1 一个主机可以有多层逻辑接口

~~~text
物理端口 ens160 ─┐
                 ├─ bond0 ─ bond0.100 ─ 三层地址
物理端口 ens192 ─┘

VRF blue ─ 对应路由表1001
    └─ ens224 ─ 三层地址
~~~

这是两种独立结构示意，不要求在同一主机同时存在。物理口、bond、VLAN子接口和VRF分别承担不同职责。看到ens160有carrier，不能替bond当前活动成员、VLAN许可或VRF查表作结论。

对普通三层接口，地址可能就在该接口上；对bond/bridge等组合，三层地址通常规划在相应逻辑接口。应先理解实际设计，再判断地址是否放错位置，不能一律要求每个物理口都配置IP。

~~~bash
ip -br link show
ip -d link show
ip -br address show
~~~

先用简表看全貌，再用详细输出确认type、master、lower device、MTU等关系。接口名由系统和配置决定，本身不能证明它连接的是业务网、管理网或哪台交换机。[接口命令参考](https://man7.org/linux/man-pages/man8/ip-link.8.html)

### 3.2 管理状态、下层状态与业务状态

下面的片段只用于解读字段：

~~~text
ens160: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 state UP
ens192: <NO-CARRIER,BROADCAST,MULTICAST,UP> mtu 1500 state DOWN
lo:     <LOOPBACK,UP,LOWER_UP> mtu 65536 state UNKNOWN
~~~

UP标志表达管理上启用；LOWER_UP由驱动等反映下层状态。ens192可以管理上启用而没有carrier。lo等设备出现UNKNOWN不应直接视为故障，需要按设备类型解释。

物理接口carrier正常，也还没有证明VLAN、路由、安全策略、对端服务和回程。虚拟接口的下层条件还取决于其具体实现。详细语义见[Linux接口运行状态](https://docs.kernel.org/networking/operstates.html)。

### 3.3 地址存在还要看属性

~~~bash
ip -4 address show dev ens160
ip -6 address show dev ens160
~~~

核对地址、前缀、scope和有效期。IPv6还需关注tentative、dadfailed、deprecated等状态；不能只看文本中出现目标地址就认为可正常选用。scope global并不等于公网地址，私有地址也可有global scope。

普通地址配置经常伴随生成前缀路由，但noprefixroute、接口状态和VRF等条件会影响结果，应实际查表，不把“配了地址”代替“已有所需路由”。[地址属性参考](https://man7.org/linux/man-pages/man8/ip-address.8.html)

## 4. Linux路由：先选查表规则，再在表内匹配

### 4.1 ip route默认只展示main表

~~~bash
ip -4 rule show
ip -4 route show table main
ip -4 route show table local
ip -4 route show table all
~~~

main是常用普通路由表；local包含本地交付等特殊路由。名称为default的表与路由条目default是不同对象：前者是一个表，后者通常表示默认前缀。不要因为系统存在default表，就认为已配置互联网出口。

典型初始IPv4规则可呈现为：

~~~text
0:       from all lookup local
32766:   from all lookup main
32767:   from all lookup default
~~~

RPDB按优先级处理规则，较小priority数值先执行。实际系统可能增加源地址、mark、入口接口、VRF等条件，应以当前输出为准。规则匹配后执行动作；若普通表查找没有得到可终结结果，可能继续下一条规则，而不是每匹配一次就必然结束。相关机制见[ip-rule手册](https://man7.org/linux/man-pages/man8/ip-rule.8.html)。

### 4.2 读一条路由，而不是只找default

~~~text
default via 10.10.10.1 dev ens160 proto static metric 100
10.10.10.0/24 dev ens160 proto kernel scope link src 10.10.10.10
203.0.113.0/24 via 10.10.10.254 dev ens160 proto static
~~~

目的前缀决定该条路由的匹配范围；via是下一跳；dev是出口；src给出该条路由的首选源地址信息，应用仍可能已绑定另一个源。proto用于标识路由来源类别，不是这个业务包使用的TCP/UDP协议。

同一表内先考虑最长前缀匹配，metric不用于让有效默认路由覆盖更具体路由。metric也不能脱离具体安装/选路条件，被当作所有协议通用的设备管理距离。

### 4.3 不要把所有表合起来做一次最长匹配

规则可能先查表100，若表100的默认路由已提供有效结果，就不会因为main另有更具体路由而自动改查main。更具体只在相应查表过程中比较，不能跨所有表无条件全局挑选。

这个差异是“明明看到正确路由，为什么还是走错”的关键。table all适合盘点，不表示内核会对其中所有条目做一次统一最长匹配。

## 5. 完整例题：双网卡主机为什么回应错出口

### 5.1 已知条件

~~~text
ens160：10.10.10.10/24 → 网关10.10.10.1，管理/默认出口
ens192：10.20.20.10/24 → 网关10.20.20.1，业务出口
远端：203.0.113.80
~~~

本节假定接口、下一跳、远端路由和过滤均满足条件，暂不讨论NAT。203.0.113.0/24是文档地址，只用于举例。

main表含默认路由经ens160，以及203.0.113.0/24经10.10.10.254。表100有默认路由经10.20.20.1/ens192。另有以下规则：

~~~text
0:       from all lookup local
100:     from 10.20.20.10 lookup 100
32766:   from all lookup main
32767:   from all lookup default
~~~

### 5.2 两个源地址会得到不同结果

源为10.10.10.10时，规则100不匹配，进入main后采用203.0.113.0/24。源为10.20.20.10时，规则100匹配，表100默认路由已提供结果，选择ens192。

| 查询条件 | 决策过程 | 教学预期 |
|---|---|---|
| from 10.10.10.10 | local无目标本地路由；规则100不匹配；main匹配/24 | via 10.10.10.254，ens160 |
| from 10.20.20.10 | local无目标本地路由；规则100查表100 | via 10.20.20.1，ens192 |

如果应用绑定业务地址，而你用不带源的测试观察到管理出口，就不能用该测试代表应用。反过来，应用未绑定源地址时，实际选源也不能凭“它是业务网卡”来猜测。

~~~bash
ip -4 route get 203.0.113.80 from 10.10.10.10
ip -4 route get 203.0.113.80 from 10.20.20.10
ip -4 route show table 100
~~~

### 5.3 源地址不对称不必然故障

源地址与出口的组合是否允许，取决于上游源校验、返回路由、状态设备及业务要求。双网卡不意味着每个源自动“从自己的网卡返回”。先说明期望，再用实际查表和抓包比较。

若来源地址未命中策略，或业务地址发生变化，main默认出口可能成为实际返回路径。修复应针对地址与路由意图，不应通过不断调整默认metric碰运气。

## 6. route show、route get和真实流量各自证明什么

route show展示条目；route get按指定查找条件求解；真实抓包和应用验证说明实际发生了什么。一次route get不会替你发包，也不验证ARP、安全规则、远端服务或返回路径。[查询语法与边界](https://man7.org/linux/man-pages/man8/ip-route.8.html)

~~~bash
# 默认按本机输出方向查询
ip -4 route get 203.0.113.80

# 复制已知的本机源地址条件
ip -4 route get 203.0.113.80 from 10.20.20.10

# 指定进入该主机的接口，用于分析转发查表
ip -4 route get 203.0.113.80 from 198.51.100.10 iif ens192

# 已确认业务在查表时带有mark 0x10，才复制该条件
ip -4 route get 203.0.113.80 from 10.20.20.10 mark 0x10
~~~

这些查询代表不同假设，不是四条命令永远依次运行。不要为得到期望结果而随意增加mark或oif；oif会约束查找，不再代表一个没有绑定出口的应用。

真实报文的mark、NAT、socket绑定、VRF和后续重查都可能影响结果。带iif的查询也不证明ip_forward或FORWARD策略已允许。查询与真实抓包不一致时，先核对条件，而不是立即认定内核错误。

## 7. 下一跳交付：有路由还没有走完整条路径

~~~bash
ip -4 neigh show dev ens160
ip -4 neigh show dev ens192
~~~

有via时，普通以太网交付重点检查下一跳的邻居条目，而不是跨网段目的主机的MAC。INCOMPLETE表示解析尚未完成；FAILED说明解析尝试失败；STALE本身不意味着当前业务失败，应结合后续探测和流量观察。

例：路由选择ens192经10.20.20.1，邻居一直INCOMPLETE。此时优先调查网关、VLAN、二层路径和ARP过滤等，不要先修改到203.0.113.80的更具体路由。反之，ARP成功也只完成了当前链路上的一段条件。

邻居缓存具有状态和时效，清空后暂时恢复不自动证明缓存是根因。先保存原状态、抓包与时间关联，再判断地址冲突或邻居更新等解释。[邻居状态参考](https://man7.org/linux/man-pages/man8/ip-neighbour.8.html)

## 8. Linux VRF：设备、表、接口与应用要连起来

### 8.1 VRF和单独路由表的区别

以下是独立于前面双出口例题的示意：

~~~text
blue（VRF设备） → table 1001
    └─ ens224：10.30.30.10/24

默认上下文 → 通常按其规则查main等表
~~~

VRF设备关联路由表，接口成为其成员，l3mdev相关规则把对应查找导向该表。不要因为有table1001就认定某业务已属于blue；还要确认接口及流量上下文。

Linux VRF聚焦三层路由域，不提供完整namespace式网络栈隔离，也不应被当作防火墙授权策略。其模型见[Linux内核VRF文档](https://docs.kernel.org/networking/vrf.html)。

### 8.2 查询对象关系

~~~bash
ip vrf show
ip -d link show type vrf
ip link show master blue
ip -4 address show dev ens224
ip -4 route show vrf blue
ip -4 route show table 1001
ip -4 rule show
ip -4 route get 10.30.30.80 vrf blue
~~~

先用ip vrf show确认名称到table ID的关联，再查成员、地址和表内路由。最后的查询显式选blue，不能据此推断默认上下文也能访问同一个目标。

上级优先规则可能先于l3mdev规则生效，因此VRF排错仍要看RPDB。接口加入VRF还会影响local/connected路由及依赖接口的其他路由；迁移时要保存并核对前后变化，不能在远程管理口直接试验后假定所有路由自动保留。

### 8.3 应用不会仅因目的地址就自动进入VRF

应用可通过socket相关接口关联VRF。ip vrf exec也可让所启动程序创建的相应socket带上关联，但依赖cgroup v2、相应内核支持和权限。它与进入network namespace不同。[ip-vrf机制和运行条件](https://man7.org/linux/man-pages/man8/ip-vrf.8.html)

~~~bash
# blue已由实验环境正确创建，目标也实际存在时才做对比
ping -c 3 10.30.30.80
sudo ip vrf exec blue ping -c 3 10.30.30.80
~~~

两次结果不同并不矛盾，它们可能使用不同上下文。还要区分测试工具能按VRF工作，与业务服务是否正确绑定。某个进程也可使用多个不同绑定的socket，不能把进程名当成所有连接的统一证据。

### 8.4 路由隔离还涉及服务监听

0.0.0.0监听不能单独证明服务会接受所有VRF来的连接。需检查socket绑定、应用VRF支持、tcp_l3mdev_accept/udp_l3mdev_accept等实际配置与本机策略。本篇仅建立这条检查边界，具体socket选择在后续专题深入，不以打开全局跨VRF接收选项作为通用修复。

## 9. 三个故障案例怎样收敛

### 案例A：接口UP，有地址，但网关不通

先确认物理/逻辑层次与carrier，再核对地址、VLAN、实际出口与邻居。若选路正确而ARP无人应答，把观测点移动到对端和交换路径；若地址本来属于另一个namespace，先修正观测上下文。

反证：如果邻居可解析且网关确实收到ICMP，只是它不回应，那么不能继续用“ARP失败”解释。业务通不通需要独立测试，网关可能限制ICMP。

### 案例B：main有业务/24，但应用却走默认出口

记录应用实际源地址、VRF与mark；按RPDB顺序检查命中表。如果先查的表100含有效默认，main的/24不会自动夺回流量。按意图修正规则或相应表，而不是只在main反复补路由。

反证：若带完整查找条件仍选预期出口，而实际抓包从另一口发出，继续核对socket约束、转换/重查及观测位置，不能把静态查表当最终事实。

### 案例C：VRF显式测试成功，服务客户端失败

区分测试工具的VRF关联与实际进程socket；检查解析得到的地址、服务绑定、过滤和回程。若客户端SYN到达服务接口而没有有效响应，调查服务处理与返回，不能只看blue表有路由就宣布网络完成。

## 10. 一套可复核的只读调查顺序

先写清源、目的、协议、进程和上下文，再按下列顺序取证；并非每个故障都要无差别运行全部命令。

| 顺序 | 观察对象 | 要回答的问题 |
|---|---|---|
| 1 | namespace/VRF/进程上下文 | 我观察的是出问题的那套网络吗？ |
| 2 | ip -br link、ip -d link | 逻辑关系与链路条件正确吗？ |
| 3 | ip address | 地址在正确对象且可用吗？ |
| 4 | ip rule、相关表 | 哪些条件决定查表，在哪一步结束？ |
| 5 | 带条件route get | 实际业务条件预期得到哪个出口与源？ |
| 6 | ip neigh | 下一跳当前能交付吗？ |
| 7 | 双端/适当位置抓包 | 报文真实走到了哪里？ |
| 8 | 服务与回程证据 | 从接口交付到业务成功还缺什么？ |

保存命令、执行位置、时间、版本和原始文本；重要计数记录前后增量。遇到平台“不支持”，保留该结果并检查能力，不把命令报错直接当网络故障。

## 11. 自测与参考解析

1. main有203.0.113.0/24，较高优先级规则导向的表100只有默认路由，应该走谁？
   - 若规则匹配且表100默认提供终结结果，采用表100；不跨表统一挑/24。
2. ens192管理上UP但NO-CARRIER，应该先修改远端业务路由吗？
   - 先检查下层连接与逻辑关系。路由不能补偿必要链路条件缺失。
3. route get返回正确via/dev，可否认定TCP443可访问？
   - 不可，它没有验证邻居、过滤、服务、真实流量与回程。
4. ip neigh中网关STALE应否立即删除？
   - 不应仅凭STALE判断失败，要关联后续状态、抓包与业务。
5. 给ens224加入blue之后，main中看不到原来的直连路由是否一定异常？
   - 先查blue关联表，VRF会改变路由上下文；再核对其他依赖路由是否需重建。
6. 显式VRF ping成功，能否证明业务进程使用相同VRF？
   - 不能，需要确认实际socket和测试上下文，而非只看目标IP相同。
