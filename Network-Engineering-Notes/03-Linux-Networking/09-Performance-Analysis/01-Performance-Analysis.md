# 从基线到瓶颈的性能分析

[Linux学习目录](../Linux-Networking.md)

## 1. 性能测试先写清测什么

“网络慢”至少可能表示连接建立慢、吞吐低、尾延迟大、丢包多或作业完成时间长。不同目标需要不同负载和测量点。ping测ICMP往返，不是交易应用精密单向时延；iperf3测测试流吞吐，不是所有业务的完成能力。

每次先记录目标、路径、软件/驱动版本、包长/消息、流数、方向、时长、负载水平与环境限制。VM用于流程和功能，不把虚拟调度抖动解释成真实ASIC性能。

## 2. 指标与单位

| 指标 | 第一遍的理解 | 必须说明 |
|---|---|---|
| Throughput | 单位时间有效传送量 | Gbit/s、GB/s或GiB/s及统计层 |
| PPS | packets per second，每秒包数 | 包长、线上开销与方向 |
| RTT | 请求往返时间 | 协议、负载与测量边界 |
| 单向时延 | 两点之间一次传送耗时 | 时钟同步、时间戳位置与误差 |
| 分位数 | 排序后指定比例位置的样本值 | 样本量、时长、算法与丢弃样本 |
| Loss/retrans | 丢失或重传相关观测 | 在哪层统计，不将两者等同 |

100Gbit/s十进制换算为12.5GB/s，不含所有协议开销。64bytes payload、64bytes以太帧和64bytes IP包不是同一口径，pps预算先定义长度。

## 3. 基线要先稳定

先验证接口、路由、MTU、邻居、监听与安全；排除功能失败后再测性能。保存空闲与负载基线，预热后正式采样，至少做几次相同条件对比。只有一次数字无法判断波动和重复性。

观察源端也观察接收端：发送程序、接收程序、CPU、队列、socket、网络路径可能任一成为瓶颈。测试器能力也是系统的一部分。

## 4. iperf3的客户端与服务端

iperf3是吞吐测试程序，-s启动服务端，-c指定服务端地址；默认常用TCP5201，UDP模式也需要相应控制连接。工具需在两端兼容安装，不对不受控公网目标压测。

以下基于已完成[实验L1](../../../Network-Career-Lab/01-Linux/02-Labs.md)的ncl-c与ncl-s。服务端在独立终端运行：

~~~bash
sudo ip netns exec ncl-s iperf3 -s -B 10.20.0.2
~~~

-B绑定服务器实验地址，避免把示例理解成所有接口公开服务。完成后在该终端Ctrl+C停止。客户端终端执行：

~~~bash
sudo ip netns exec ncl-c iperf3 -c 10.20.0.2 -t 15 -i 1
~~~

-t 15表示15秒测试，-i 1每秒报告，默认这一方向由客户端发送。记录sender与receiver统计，它们受统计区间等影响，不能简单把二者差额当精确线路丢失。

## 5. 一次只增加一个变量

~~~bash
# 比较反方向
sudo ip netns exec ncl-c iperf3 -c 10.20.0.2 -t 15 -R

# 比较四条并行TCP流
sudo ip netns exec ncl-c iperf3 -c 10.20.0.2 -t 15 -P 4

# UDP：明确目标速率与数据报长度
sudo ip netns exec ncl-c iperf3 -c 10.20.0.2 -t 15 -u -b 100M -l 1200
~~~

-R反转发送方向，-P指定并发流数，-u用UDP，-b设置目标bit/s，-l在此UDP示例指定数据报长度。UDP目标100M不保证实际达到，接收侧loss/jitter也只属于测试协议和工具口径。不同iperf3版本的线程/功能实现可能不同，应记录版本。[iperf3官方参数](https://software.es.net/iperf/invoking.html)

veth两端同机的结果会共享宿主CPU和内存，不证明物理链路速率、光模块、线缆或NIC能力。这里用于理解方向、并发和统计。

## 6. 吞吐低的四条证据链

| 假设 | 支持线索 | 区分/反证 |
|---|---|---|
| TCP在途量不足 | 高RTT、窗口/拥塞限制、单流低 | 固定条件比较窗口统计与并发 |
| 路径丢弃/MTU | 重传、包长相关失败、ICMP | 双端抓包与递增包长 |
| 主机处理不足 | 单核高、队列/socket丢弃 | 每核/每队列/应用同步采样 |
| 其他资源或限速 | tc整形、PCIe/存储/应用受限 | 查相应配置、资源与替代负载 |

带宽时延积可估算在途量：10G、RTT20ms约25MB，但不以一条算式替代所有其他检查。多流快不等于单流也被优化；反向慢不等于网络一定不对称，端点角色也交换了。

## 7. 低平均利用率仍可能排队

如果总到达800G、出口400G，持续10µs，理想净积压约500,000bytes。过后很快排空，分钟级平均仍可低。端口平均不能替代队列峰值、丢弃、采样精度与业务时间窗。

Buffer加大可能减少突发丢失，但也可增加等待；ring和socket缓冲同样不能无限弥补持续消费不足。性能验收必须同时看用户目标与资源代价。

## 8. 教学案例：UDP行情缺口，链路很空

以下是模拟数据，用于练习推理，不是本次测试结果：

| 同一负载窗口 | 交换机相关出口丢弃增量 | R1的UDP接收缓冲错误增量 | R1应用gap |
|---|---|---|---|
| 基线 | 0 | 0 | 0 |
| 异常 | 0 | 800 | 800 |
| 调整后 | 0 | 100 | 100 |

计数相关支持调查R1接收/消费，但不能凭相等数字证明每个gap都一一来自同一层。检查统计覆盖、其他流、应用序号、时间对齐和记录器drop。

若只增大缓冲后gap少了，还要测排队等待是否增加，以及持续更长时间是否仍溢出。只有应用消费能力与规定负载都满足，才能说明方案可持续。

## 9. 尾延迟与时钟误差

平均值掩盖少量长等待。p99/p99.9需要足够样本，20次ping不能支撑稳定的p99.9结论；还要说明超时请求如何计入，不能删除最慢样本后再宣称改善。

两主机时间戳相减要求可比较时间基准和位置。若两端各有±0.5µs误差，差值最坏可达±1µs，尚未包含路径/时间戳误差。记录纳秒格式不代表具备纳秒准确度。[Linux时间戳机制](https://docs.kernel.org/networking/timestamping.html)

## 10. 实验设计与恢复模板

实验表至少包含：唯一变更、原值、假设、固定条件、重复次数、指标、预期、实测、反证、恢复动作和恢复后基线。不能同时改MTU、offload、CPU绑定和拥塞算法再挑其中一个当根因。

收益也要有代价：CPU、内存、功耗、兼容、运维、监控能力。只比较最佳一轮容易被噪声误导；保存原始结果与完整失败记录。

## 11. 分层验收与自测

第一层功能：正常/故障/恢复证据。第二层性能：固定负载可重复测量。第三层应用：真实请求或业务序号达标。不要把第一层完成写成物理性能验证。

自测：RTT/2是否总等于单向？答案：需对称等假设。p99改善、丢包增加是否一定更好？答案：按业务验收综合判断。iperf3高是否证明磁盘应用也快？答案：不是。

交付一份TCP或UDP调查报告、一组重复结果和一个未被证明的剩余问题。本篇只提供方法与命令，未执行实际压测。
