# 综合案例：从主机不可达走到性能瓶颈

[Linux学习目录](../Linux-Networking.md)

## 1. 案例怎样使用

以下为教学情境，不是你的生产经历，也不是本次实测。先遮住参考判断，写下候选解释与所需证据；再比较你的分析有没有跳过Linux组件。每个案例都要区分恢复业务与确认根因。

## 2. 案例A：SSH连不上，但网关能ping

已知：客户端到服务器网关ICMP正常，TCP22失败。不能用网关可达代替服务器可达，也不能假定所有系统SSH端口为22。

调查顺序：确认服务器实际地址与服务端口→查相应空间监听→看服务状态/日志→双端抓SYN→核对过滤与返回。若服务监听127.0.0.1:22，说明地址范围可能不覆盖远端访问；若SYN根本不到服务器，服务绑定不能解释这段缺失。

参考结论格式：“在服务器接口抓到请求，但ss没有对应地址/端口监听；服务日志显示端口占用；修复冲突后同一请求恢复。”若没有这些证据，就保留其他解释。

## 3. 案例B：宿主能访问，容器/namespace不行

宿主地址/路由不属于端点的同一套状态。进入端点查接口、地址、路由和DNS，沿veth→bridge→路由/NAT路径画图。若端点与网关不在正确VLAN，宿主main表正确不能补偿。

参考区分：端点未发出请求，看本机路由/解析；veth出而bridge后无，看二层和过滤；宿主外侧已发出而返回丢失，看转换/回程。每个位置还要核对采集覆盖。

## 4. 案例C：HTTP小响应快，大文件挂住

保留MTU/反馈、拥塞丢弃、TCP窗口和应用/磁盘四种解释。看大段重传与ICMP、连接窗口、负载期队列、应用日志；递增包长只是区分实验之一。

若降低MSS绕过现象，只说明包长相关解释值得深入，不自动确定哪一跳隧道或策略错误。修复要回到封装预算与必要反馈，恢复后用原负载验证。

## 5. 案例D：单流低、多流高

可能是窗口/RTT、单队列/核心、应用串行或路径hash。同步记录ss -i、各核、队列和PCIe能力，不能只用总CPU。

如果一核高且单流集中，支持处理瓶颈；若CPU空闲但窗口/RTT上限吻合，调查传输限制；若两端都不受限，则继续检查整形与远端。多流也会改变总负载和资源分布，不能把改善单独归功某个参数。

## 6. 案例E：UDP gap与平均利用率低

从频道/序号/时间窗开始，比较接收机和A/B路径。查短时队列、NIC、内核、socket、应用和记录器自身drop。平均5分钟利用率不能排除微突发，pcap缺序号也不能排除采集丢包。

若socket错误与gap同窗上涨，继续验证应用消费、CPU竞争与缓冲，而非只调交换机。增大buffer后必须检查等待时间和长时间稳定性。

## 7. 案例F：调优后最佳值更好，业务投诉更多

检查是否牺牲尾延迟、其他流、CPU/功耗、故障后容量或监控能力。确认负载与样本相同，超时是否被删掉，是否只选最佳一次。

恢复原值后重跑基线；若差异无法稳定复现，结论应写“当前证据不足”，不把猜测做成全网模板。

只有网络原理正确、Linux对象位置明确、证据能复核和恢复完整，才算相应能力通过。教材文件完成不代表你已经完成实验或具备生产经历。
